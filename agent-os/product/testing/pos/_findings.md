### Finding #8 — root cause + fix (2026-07-03)

**Which problem:** display-only. The persisted ledger value was never wrong.

- **Bug (display):** `shift-close-panel.tsx` unconditionally sourced its summary from the local IndexedDB queue via `computeLocalZReportFromQueue(db, openingFloat)` — regardless of connectivity. Expected cash, transactions, net/cash sales, and the derived over/short all came from local IDB; it received `serverShiftId`/`isOffline` props but never used them, and always rendered the WifiOff "Offline totals" note (the "Offline while Online" tell). When the device's local queue trailed the server (sales rung on another device/session, or a cleared/partial IDB — the prod case: 8 local vs 10 server), the cashier saw a wrong expected (1,795.720 vs true 1,827.720) and a phantom over/short. The X-report dialog was already correct — it uses the server `useXReportQuery`.
- **Persisted value (safe):** `PosShiftsService.close` (`pos-shifts.service.ts:477-479`) recomputes `expectedCash` via `computeCashComponents` (DB aggregate over `pos_payments`/`pos_transactions`/`pos_cash_movements`) and `cashOverShort = actualCash − expectedCash` server-side; it only trusts client `actualCash` (the physical count). GL was correct (1,827.720). Already guarded by `pos-shifts.service.spec.ts` (close computes expected/over-short from DB, ignores client figures).
- **Fix:** when `!isOffline && serverShiftId`, the close panel now drives expected/summary/over-short from the server X-report (`useXReportQuery`), labelled "Live totals from the server"; the local IDB report is used **only** offline / pre-sync, labelled provisional. Panel also nudges the sync engine on open so pending local sales flush. New regression guard `shift-close-authoritative.test.tsx` reproduces the exact 8/1,795.720 (local) vs 10/1,827.720 (server) divergence and asserts the online close reconciles against the server tally with no phantom over/short. web typecheck + i18n:check + close-panel tests (8) green.
- **Also addresses #7's contradiction:** the "Offline totals" note now renders only when actually provisional/offline. (The duplicate helper/placeholder text in #7 is cosmetic and left as-is.)

### Finding #17 — D1 decision REVERSED: never-block-and-flag (2026-07-05)

**Supersedes the block-at-completion decision above.** Founder ruling: a physical till must **never** refuse a real sale because system stock is behind physical reality (received-but-not-entered, quantity-typed sales, multi-channel drift, stale offline snapshots). A batch-tracked oversell must now **complete, relieve negative, and flag** — exactly like non-tracked items — instead of being blocked. The prior fix (`assertBatchLotsAttributable`, commit `f48888ca`) is **removed**.

**What shipped (engine-level, the durable fix):**
- **`BatchPickerService.pick`** gains `opts.allowNegative`. Never-block: consume all available lots FEFO, then place the shortfall as a **negative quantity on the latest-expiry lot** (a real `batch_id` — the `failUnattributed` never-null invariant is respected). If the item has **no lots at all**, find-or-create a per-item **reconciliation lot** (`"UNRECEIVED (auto)"`, race-safe). Strict mode (default, `allowNegative:false`) is byte-identical — still throws for non-POS.
- **`MovementAttributionService.attributeOutbound`** threads `AttributionInput.allowNegative` into `pick()`. Serial issues are **not** relaxed by the flag.
- **`inventory-event.listener.applyOutbound`** sets `allowNegative = !payload.blockNegativeStock` (POS ⇒ true). COGS JE + signed stock movement + `decrementOutbound(flexible)` + `NEGATIVE_STOCK_FLAG` all post on the oversell → **three-way tie-out holds on a negative sale.**
- **`pos-transactions.service.pay`** — `assertBatchLotsAttributable` (call + method) **deleted**; no pre-completion batch block.
- **`pos-sync.service`** — offline oversell now relieves-negative + flags on sync (no dead-letter); comment corrected.
- **Serials keep blocking** — a serial the system has no record of cannot be attributed (a negative serial has no physical meaning; null `serial_number_id` would break `failUnattributed` → warranty/recall/return-matching). Message made actionable: *"Serial 'X' is not in the system yet. Receive or quick-add this unit, then ring the sale again."*
- **Flag surfacing** — deliberately **NOT denormalized** (derive-don't-denormalize, per AP-subledger principle). Negative stock is already ledger-truth on the **Stock Levels report** (`deriveStatus`→`negative` badge + `negativeStockCount`, `msl_zero_or_negative_stock_idx` partial index). That is the manager's reconciliation surface; the `NEGATIVE_STOCK_FLAG` event is kept for future consumers.

**Residuals R1/R2 DISSOLVED** — both only existed because a *block* needed a *reservation* to be race-safe. With never-block there is nothing to race on (concurrent same-lot sales both complete; the lot just goes further negative), so **no reservation table is needed**. Offline and online now converge on relieve-negative + flag.

## Finding #20 (CRITICAL) — never-block batch oversell never actually worked; three-way tie-out silently broke on a cash-completed sale (DEV-446, 2026-07-05)

**Supersedes Finding #17 "D1 REVERSED — never-block-and-flag (SHIPPED)".** That change hardened `BatchPickerService.pick(allowNegative)` — but a pre-launch verification pass against **real code + migrations** (not the mocked unit tests) found the POS batch-oversell flow never reaches it, and instead **rolls back the inventory relief**. The 414 green unit tests hid this because they mock the DB (the CHECK never runs) and call `pick()` directly (a path POS does not take).

**Root cause — three latent defects, all confirmed against source:**
1. **Add-line hard block** (`pos-transactions.service.ts:415-419`, untouched by the #17 diff): a batch item with no active/expiring lot holding `qty_remaining > 0` threw `"No available batch found…"`. A fully-depleted batch item could not even be added to the cart. The till refused a real sale — the exact thing never-block forbids.
2. **CHECK-constraint rollback on a partial oversell**: POS stamped an explicit FEFO `batchId` at add-line (`:421`) and `buildLineItems` (`pos-transactions-totals.ts:283`) put it on the payload, so `attributeOutbound` took the **explicit-batchId branch — which ignored `allowNegative` and never called the picker**. The async relief's `StockLedgerService.incrementBatchRemaining` does `qty_remaining + (negative delta)`; on a lot with 3 selling 10 → `3 + (-10) = -7` → violated `item_batches_qty_remaining_non_negative` (migration 0145) → the relief transaction rolled back → the outbox dead-lettered → **COGS JE + stock movement never posted while the cash sale completed and the receipt printed.** Silent three-way tie-out break (the Finding #17/#18 failure class) + a potential outbox circuit-breaker stall for the tenant.
3. The shipped `allowNegative` picker machinery (negative-on-lot, reconciliation lot, FEFO fan-out) was **unreachable from POS**.

**Founder decision (2026-07-05): Option A — engine-picks-at-relief.** Long-term-correct; accounting-reviewed money-correct **and necessary** (fils-accurate tie-out proven for both the recon-lot and negative-on-existing-lot scenarios; the change is required because the CHECK currently rolls the sale back).

**What shipped (branch `phase-4a/dev-446-pos-never-block-tie-out`):**
- **Migration 0154** drops `item_batches_qty_remaining_non_negative`. `qty_remaining` is now a pure **ledger projection** (= Σ ledger.quantity per batch) that MAY go negative on an oversold lot; a loud schema comment forbids ever re-adding the CHECK (`packages/db/src/schema/item-batches.ts`).
